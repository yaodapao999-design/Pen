# 文档驱动开发（DDD）在本项目中的含义

文档驱动开发不是“多写文档”，而是把**可执行的事实**分层沉淀：先冻结意图与边界，再给出可落地的实现方案与脚本契约，最后用编辑器配置把可调参数讲清楚。代码与场景改动应当能**回溯到文档**，文档之间也能**互相链接、同步演进**。

## 核心理念

- **单一事实来源（按层）**：每一层只回答一类问题，避免把设计、实现、配置混在同一段文字里。
- **先对齐，再动手**：在写 `.cs` 前，先把类型职责、API、数据流、文件路径与 Inspector 暴露字段写清楚，减少返工与隐性约定。
- **可追溯**：任何实现都应对应一份实现计划；实现计划又被 GDD 链接；配置说明必须能对应到真实脚本字段。
- **可验收**：测试计划与 Checklist 把“完成”定义成可勾选的结果，而不是主观感觉。
- **同步演进**：当上级文档变化时，下级文档与脚本契约需要跟着检查（本仓库用 Cursor Hook 做启发式提醒）。

## 文档层次（自上而下）

与 `/.cursor/rules/plan-output.md` 对齐的四个层级：

1. **游戏设计（GDD）**：`Assets/Plans/<GDD名>/game-design.md` —— 做什么、为什么、边界与非目标。
2. **实现计划**：`Assets/Plans/<GDD名>/implementation/<purpose>.md` —— 怎么做；包含可编码结构与变更清单。
3. **实际代码**：仓库中的 **`.cs` 脚本文件本身**（不是计划 md）。实现计划里用 `## 实际代码层（CS 脚本）` 把脚本路径、类型、Inspector 字段与 API **写成契约**。
4. **配置指南**：`Assets/Plans/<GDD名>/editor-setup.md` —— 在 Unity Editor 中如何配置；**覆盖所有可见参数**并与第 3 层的字段清单一致。

## 写作与协作上的“硬规矩”（精髓）

- **一 GDD 一目录**：`Assets/Plans/<GDD名>/`；一个 GDD 可以对应多个 `implementation/*.md`。
- **GDD 必须链接所有实现计划**：用相对路径列出 `./implementation/...`。
- **实现计划必须包含 Checklist**：把编码、集成、测试、文档同步拆成 `- [ ]` 可勾选项。
- **默认不读场景/预制体文本**：除非用户明确授权或点名路径（见 `/.cursor/rules/unity-context.md`）。
- **文末更改日志**：GDD、实现计划、配置指南都要有 `## 更改日志`，记录日期/版本与摘要。

## 这套方法解决什么问题

- **独立游戏常见痛点**：需求口头化、Inspector 调参不可追溯、Prefab/场景改动与脚本契约漂移。
- **把不确定性前移**：在文档层暴露歧义与风险，而不是在编译/联调阶段爆炸。

## 延伸阅读（仓库内）

- `/.cursor/rules/plan-output.md`：Plan 产出路径、章节模板与强制清单。
- `/.cursor/rules/unity-context.md`：Unity 文本资源（`.unity/.prefab`）读取策略。
